# Spike 014: 연습용 프로젝트 여섯의 시간과 배치

## What This Validates

spike 006 (GitHub runner 의 첫 분석 약 43초) 과 008 (plugin 폴더는 패키지 루트 경로마다 따로 생긴다) 이 맞물리는 자리다. 03-CONTEXT.md 가 계획에 맡긴 두 가지 — "plugin 을 쓰는 연습용 프로젝트 넷이 plugin 준비를 나눠 쓸 수 있는지", "샘플 소스를 여섯이 나눠 쓰는 방법" — 과, 논의 때 추정으로만 적은 자동 점검 시간(약 4분 15초)의 근거를 로컬에서 잰다.

- **Given** D-03 의 연습용 프로젝트 여섯 (옛 주소 / 묶음 / 기본만 / 끄는 설정 / 기본 + Riverpod / 기본 + codegen — plugin 을 쓰는 것이 넷)
- **When** 차례로 또는 동시에 분석하면
- **Then** 전체 시간과 배치 방식에 따른 차이가 재어지고, 어느 방식에서도 진단이 예상과 같다

## Research

- spike 008: plugin 폴더의 이름은 분석 대상 패키지 루트 경로의 md5 다. 경로가 다르면 폴더가 따로 생기고 plugin 을 따로 컴파일한다 (약 13초). 전용 상태 폴더에 plugin 폴더가 하나일 때만 검증 명령이 버전을 읽는다. 빈 상태 폴더를 동시에 **함께** 쓰면 드물게 깨지고, 상태 폴더를 **따로** 주면 동시에 띄워도 문제가 없었다 (2쌍).
- spike 006: GitHub Linux runner 의 첫 분석은 약 43초 (27 ~ 53초), 재실행은 약 8초. 로컬은 약 15초 / 3.5초다.
- `tool/verify.dart` (지금): `fixtures` 목록을 차례로 돌며 `.dart_tool/woody_verify/<이름>/` 을 상태 폴더로 준다 — 아래의 방식 A 를 하나짜리로 쓰고 있다.

| Approach | Tool/Library | Pros | Cons | Status |
|----------|-------------|------|------|--------|
| A. 폴더마다 따로, 상태 폴더도 따로 | 지금의 검증 명령을 여섯으로 늘림 | 코드가 그대로 늘어난다. 상태 폴더마다 plugin 폴더가 하나라 버전 읽기가 그대로다. 프로젝트마다 열어 볼 수 있다 | 처음 실행에서 plugin 을 넷 컴파일한다 | **잼 — 기준** |
| A'. 폴더마다 따로, 상태 폴더는 하나를 함께 | 상태 폴더 경로만 바꿈 | 분석 캐시를 나눠 써 조금 빠르다 | plugin 폴더가 넷이 되어 버전을 읽을 수 없다. 컴파일은 여전히 넷 | 잼 — 쓰지 않음 |
| P. A 를 동시에 띄움 | `Future.wait` | 벽시계 시간이 3분의 1 | 화면에 찍는 순서를 따로 맞춰야 한다. 코어가 적은 runner 에서의 이득은 재지 않았다 | 잼 — 선택지 |
| B. 작업 폴더 하나에서 옵션 파일만 바꿔 가며 | 실행할 때 복사 | plugin 을 한 번만 컴파일한다 | 커밋된 폴더가 아니라 작업 폴더를 분석한다. 복사 · 의존성 경로 · `pub get` 을 스크립트가 맡는다 | 잼 — 선택지 |
| C. 샘플을 복사하지 않고 `lib/` 를 링크로 | 심볼릭 링크 | 샘플이 한 벌이다 | Windows 의 git 은 설정에 따라 링크를 보통 파일로 받는다 (재지 않음) | 잼 — 동작은 함 |

**Chosen approach:** 여섯을 실제로 만들고 네 방식을 한 스크립트에서 차례로 돌린다. 방식마다 시간뿐 아니라 진단이 예상과 같은지를 함께 본다 — 빨라도 결과가 틀리면 쓸 수 없다.

## Investigation Trail

모두 Dart 3.13.4, `riverpod_lint` 3.1.9, macOS arm64 (프로세서 10개), 2026-10-12. 두 번 돌렸다 — 아래 표는 두 번의 값을 `첫 번째 / 두 번째` 로 적었다. pub cache 는 채워진 상태다.

첫 실행의 로그(`results/probe-run1.log`) 끝의 `pub get 여섯  259.0` 은 스톱워치를 멈추지 않은 스크립트의 잘못이고 실제 값은 같은 로그 위쪽의 `합계 1.3초` 다. 두 번째 실행 전에 고쳤다.

### 1. 방식별 합계 (로컬, 초)

| 방식 | 처음 실행 | 재실행 | plugin 폴더 | 진단 |
|---|---|---|---|---|
| A. 폴더 · 상태 폴더 따로 | 66.1 / 65.9 | 20.1 / 20.9 | 상태 폴더마다 1 | 여섯 다 예상과 같음 |
| A'. 상태 폴더 함께 | 54.7 / 56.7 | 15.0 / 15.1 | **한 폴더에 4** | 같음 |
| P. 동시에 — plugin 넷 | 벽시계 20.9 / 21.6 | — | 상태 폴더마다 1 | 같음 |
| P. 동시에 — 여섯 | 벽시계 22.8 / 23.1 | — | 상태 폴더마다 1 | 같음 |
| B. 작업 폴더 하나 | 27.2 / 28.4 | 15.2 / 15.7 | **1** | 여섯 옵션 다 같음 |

`pub get` 은 여섯을 합쳐 1.3초다 (lock 이 있고 pub cache 가 채워져 있을 때).

### 2. 프로젝트 하나의 시간 (두 번째 실행, 초)

| 프로젝트 | A 처음 | A 재실행 | A' 처음 | B 처음 |
|---|---|---|---|---|
| example (옛 주소) | 15.1 | 3.5 | 15.9 | 16.5 |
| recommended | 15.2 | 3.5 | 13.2 | 3.4 |
| base_only — plugin 없음 | 3.2 | 3.2 | **0.7** | 0.7 |
| overrides | 15.3 | 3.6 | 13.1 | 3.5 |
| base_riverpod | 13.9 | 3.5 | 13.1 | 3.5 |
| base_codegen — plugin 없음 | 3.3 | 3.6 | **0.7** | 0.7 |

- **plugin 을 쓰는 프로젝트는 폴더가 다르면 매번 컴파일한다.** 상태 폴더를 함께 써도(A') 둘째부터 13초다 — 줄어든 2초는 컴파일이 아니라 분석 캐시다.
- **빈 상태 폴더의 값은 약 2.5초다.** plugin 을 쓰지 않는 프로젝트가 빈 상태 폴더에서는 3.2초, 채워진 상태 폴더에서는 0.7초다. 그래서 A 의 재실행(20초)에서 plugin 없는 둘이 3초씩 든다 — 상태 폴더가 "비어 있지는 않지만 그 프로젝트만 쓰는" 폴더여도 같다.
- 작업 폴더 하나(B)에서는 경로가 같으므로 plugin 폴더가 하나이고, 옵션 파일을 바꿔도 다시 컴파일하지 않는다. 끄는 설정처럼 `plugins:` 를 다시 적은 옵션도 `version` 이 같으면 그대로 쓴다.
- B 에서 옵션 파일만 바꿔 같은 상태 폴더로 돌려도 여섯 결과가 모두 예상과 같았다 (처음 · 재실행 각 6번). 분석 캐시가 앞 옵션의 결과를 끌고 오지 않는다.

### 3. 동시에 띄우기 (P)

상태 폴더를 프로젝트마다 따로 주고 동시에 띄웠다.

| 무엇 | 벽시계 | 하나씩의 시간을 더하면 | 결과 |
|---|---|---|---|
| plugin 을 쓰는 넷, 처음 실행 | 20.9 / 21.6초 | 83.1 / 83.5초 | 넷 다 예상과 같음 |
| 여섯 모두, 처음 실행 | 22.8 / 23.1초 | 101.4 / 103.1초 | 여섯 다 예상과 같음 |

차례로 돌린 66초가 23초가 된다. 동시에 돌리면 하나하나는 느려지지만(15초 → 21 ~ 23초) 겹쳐 돈다. 두 번의 실행에서 20건(4 + 6, 두 번)이 모두 통과했다 — spike 008 이 2쌍으로 본 "상태 폴더를 따로 주면 동시에 띄워도 된다" 가 넷 · 여섯에서도 성립했다.

### 4. 샘플을 링크로 나눠 쓰기 (C)

`fixtures/linked/lib` 를 `../../example/lib` 로 가는 심볼릭 링크로 두고 묶음을 받게 했다.

- 정답지와 한 줄도 다르지 않았다 (16줄, exit 2, plugin 3줄). 진단의 경로는 링크를 푼 경로가 아니라 `lib/added_rules.dart` 처럼 그 프로젝트 기준으로 나온다.
- macOS 에서 본 결과다.

## Results

**Verdict: VALIDATED** — 두 번의 실행에서 48건씩 모두 성립했고, 방식별 시간이 1 ~ 2초 안에서 재현됐다.

1. **지금의 방식(A)을 여섯으로 그대로 늘려도 된다.** 로컬에서 처음 실행 66초, 재실행 20 ~ 21초다. 상태 폴더마다 plugin 폴더가 하나라 버전 읽기가 그대로 동작한다.
2. plugin 준비는 폴더가 다르면 나눠 쓰지 못한다. 나눠 쓰려면 같은 경로에서 분석해야 한다 (B — 처음 27 ~ 28초).
3. 상태 폴더를 하나로 합치는 것(A')은 얻는 것(처음 9 ~ 11초, 재실행 5초)보다 잃는 것(plugin 폴더가 넷이 되어 버전을 읽지 못한다)이 크다.
4. 동시에 띄우면(P) 여섯이 23초다.

Phase 3 의 계획이 가져갈 것:

1. **연습용 프로젝트는 폴더마다 따로 두고, 상태 폴더도 지금처럼 프로젝트마다 따로 준다** (`.dart_tool/woody_verify/<이름>/`). 상태 폴더를 합치지 않는다.
2. 샘플 소스는 프로젝트마다 복사본을 커밋하는 것을 기본으로 한다. 링크는 macOS 에서 동작했지만 다른 운영체제에서 재지 않았고, 복사본이 어긋나는 것은 "2번(묶음)은 1번(`example/`)의 정답지와 견준다" 는 구성(D-03)이 잡는다 — 샘플이 다르면 진단이 달라진다.
3. plugin 을 쓰지 않는 프로젝트(기본만, 기본 + codegen)의 상태 폴더에는 plugin 폴더가 생기지 않는다 (A 의 `plugin 폴더 0개`). 화면의 `plugin` 줄은 이 둘에서 "해당 없음" 으로 찍을 수 있다 — 지금 코드는 폴더가 0개면 `?` 를 찍는다 (`02-VERIFICATION.md` 5번).
4. 시간이 문제가 되면 먼저 P (동시에 띄우기)를 검토한다. 상태 폴더가 이미 따로라 구조를 바꾸지 않는다. B 는 가장 빠르지만 "커밋된 폴더를 그대로 분석한다" 를 포기해야 한다.

- 근거: 지금의 job 이 1분 54초이고 그중 `example/` 분석이 약 44초, 그 밖이 약 70초다 (STATE.md, run 38158088016). runner 의 재실행은 약 8초다 (spike 006). plugin 없는 프로젝트의 9초는 로컬 3.2초에 runner / 로컬 비(약 2.9)를 곱한 값이다.
- 논의 때의 추정(약 4분 15초)과 같은 자리다. `timeout-minutes: 10` 안에 든다.

확인하지 않은 것:

- GitHub Linux runner 에서의 여섯. D-09 대로 phase 를 끝내기 전에 올려서 본다.
- 코어가 적은 기계에서의 P.
- pub cache 가 빈 상태의 `pub get` (runner 의 첫 프로젝트). 여섯이 같은 패키지를 쓰므로 둘째부터는 채워진 상태다.
- Windows 와 Linux 에서의 심볼릭 링크.
- B 를 실제 검증 명령으로 옮긴 것 (실행할 때 커밋된 폴더를 작업 폴더로 복사하는 단계). 여기서는 옵션 파일만 바꿨다.
- 상태 폴더가 여섯일 때의 디스크 사용량. plugin 을 쓰는 넷마다 `plugin.aot` (spike 008 에서 약 15MB)이 생긴다.
