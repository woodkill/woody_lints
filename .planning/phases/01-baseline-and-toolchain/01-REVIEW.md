**(가) `ignore` 를 푸는 변경.** 배포 파일의 `analyzer.errors` 항목은 `lib/analysis_options.yaml:43-44` 의 `invalid_annotation_target: ignore` 하나다. `.planning/ROADMAP.md` 의 Phase 3 결정 사항 D7 은 이 줄을 "`codegen.yaml` 로 옮길지 **삭제할지**" 를 선택지로 둔다. 이 진단의 기본 등급은 warning 이다 (pub 캐시의 `analyzer-14.5.0/lib/src/diagnostic/diagnostic.g.dart:8530-8534`, `DiagnosticType.STATIC_WARNING`). 지우면 freezed / json_serializable 를 쓰는 프로젝트에 warning 이 나고 `dart analyze` 가 실패한다.

- 읽기 A — `errors:` 의 값이 `ignore` 에서 warning 으로 올라간 것이다. "심각도가 warning 이상으로 올라가나" 가 "예" → **major** (44행).
- 읽기 B — `ignore` 였으므로 "켜져 있던" 것이 아니다. 진단이 새로 생기는 것이다 → 2번 "errors 설정이 바뀌었나" → **minor** (46행).

56행의 이유를 대입하면 B 쪽이다 (진단이 새로 생기므로 "새로 생기는 경고" 표에 잡힌다). 25행의 문장만 읽으면 A 쪽이다.

**(나) 기준 시점.** "이미" 가 직전 릴리스(tag)를 가리키는지 직전 커밋을 가리키는지 없다. milestone 브랜치에서 앞 phase 가 규칙을 켜고 뒤 phase 가 `errors:` 로 그 규칙을 warning 으로 올리면, 커밋 기준으로는 "이미 켜져 있던 규칙의 심각도 상향" (major)이고 릴리스 기준으로는 "새로 켠 규칙" (minor)이다.

**(다) warning 을 error 로 올림.** 25행의 문장("warning 이상으로 올라가나")과 44행에는 걸린다. 56행은 범위를 "info 에서 warning 이상으로" 라고 적고, 이유("`dart analyze` 가 통과에서 실패로 바뀔 수 있다")도 해당하지 않는다 — warning 이면 이미 실패한다.

**(라) "규칙" 의 범위.** `analyzer.errors` 는 lint 규칙뿐 아니라 analyzer 가 원래 내는 진단(`invalid_annotation_target`, `dead_code` 등)의 등급도 바꾼다. 이런 진단은 누가 "켠" 것이 아니다.

**Fix:** 30행의 셋째 조건 설명에 정의를 넣는다. (가)와 (다)는 소유자가 한 문장씩 정해야 한다. 56행의 이유와 맞추면 다음과 같다.

```markdown
셋째 조건은 **이미 켜져 있던** 규칙에만 해당한다. "이미 켜져 있던" 은 직전 릴리스(tag)에서 진단을 내고 있던 것을 뜻하고, lint 규칙과 analyzer 가 원래 내는 진단을 모두 가리킨다. 직전 릴리스에서 `analyzer.errors` 로 `ignore` 해 두었던 진단을 푸는 것은 진단이 새로 생기는 것이므로 2번(minor)이고 "새로 생기는 경고" 표에 적는다. 규칙을 새로 켜는 것도 그 규칙이 처음부터 warning 이나 error 등급이어도 2번(minor)이다.
```

(다)는 둘 중 하나로 정한다 — 25행의 문장대로 major 로 두고 56행의 "info 에서" 를 지우거나, "info 였던 것이 warning 이상이 되는 경우만" 으로 25행과 44행의 뜻을 30행에서 좁힌다.
