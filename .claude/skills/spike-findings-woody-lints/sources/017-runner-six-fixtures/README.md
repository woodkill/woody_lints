# Spike 017: GitHub runner 에서의 연습용 프로젝트 여섯

## What This Validates

spike 006 (runner 에서 프로젝트 하나의 첫 분석 약 43초) 과 014 (로컬에서 여섯이 차례로 66초, 한꺼번에 23초) 가 맞물리는 자리다. Phase 3 이 끝나면 자동 점검이 연습용 프로젝트 하나가 아니라 여섯을 돈다. 그 시간은 지금까지 셈한 값(약 4분 20 ~ 30초)뿐이고, 한꺼번에 띄운 값은 추정도 없다.

- **Given** 캐시 없는 GitHub Linux runner 에 나눈 구조의 복사본과 D-03 의 연습용 프로젝트 여섯이 있을 때
- **When** 차례로 한 번, 한꺼번에 한 번 돌리면
- **Then** 진단이 로컬과 같고, 차례 실행이 시간 제한 10분 안에 끝나며, 한꺼번에 띄운 실행의 시간과 실패 여부가 기록된다

결과의 처리 기준은 03-CONTEXT.md D-07 과 같다 — 값이 어느 쪽이든 기록하고 계속한다. Phase 3 의 계획이 `tool/verify.dart` 를 차례로 짤지 한꺼번에 띄울지, `timeout-minutes` 를 얼마로 둘지를 이 값으로 정한다.

## Research

- **spike 014 (로컬, 프로세서 10개):** 차례로 처음 66초 · 재실행 20 ~ 21초, 한꺼번에 처음 23초. 한꺼번에 띄운 20건이 모두 예상과 같았다. 이때 pub cache 는 **채워진 상태**였다.
- **spike 006 (runner, 코어 4개):** 프로젝트 하나의 첫 분석 약 43초, 재실행 약 8초. 실제 `verify` job 은 1분 54초 ~ 2분이다 (Flutter 설치 약 60초).
- **spike 008:** 빈 상태 폴더를 여러 실행이 **함께** 쓰면 드물게 깨진다. 상태 폴더를 따로 주면 문제가 없었다.
- **처음 보는 조건:** runner 의 job 은 새 가상 머신이라 pub cache 에 plugin 쪽 패키지(`riverpod_lint`, `analyzer` 등)가 없다. 한꺼번에 띄우면 plugin 을 쓰는 프로젝트 넷이 **같은 패키지를 같은 pub cache 에 동시에 처음 받는다.** 로컬의 동시 실행은 이 경우를 지나지 않았다.

| 방식 | 도구 | 장점 | 단점 | 채택 |
|---|---|---|---|---|
| 작업 브랜치를 올리고 임시 workflow 로 잰다 | `git push` + 임시 workflow | spike 006 의 선례 그대로다. Phase 3 을 짓기 전에 값이 나온다 | GitHub 에 올려야 한다 (소유자 확인) | **채택** |
| Phase 3 을 끝낼 때 처음 본다 | 03-CONTEXT.md D-09 | 올리기가 한 번 줄어든다 | 차례 / 동시의 설계가 추정 위에 선다 | 쓰지 않음 |
| 로컬에서 코어 수를 줄여 흉내 낸다 | `taskset` 류 | 올리지 않는다 | macOS 에 같은 도구가 없고 빈 pub cache 를 흉내 내지 못한다 | 쓰지 않음 |

**Chosen approach:** 방식(차례 `seq` / 한꺼번에 `par`)마다 job 을 따로 둔다. 한 job 안에서 둘을 이어 돌리면 뒤의 것은 pub cache 가 채워진 상태가 되어 "동시에 처음 받는" 경우를 보지 못한다. job 마다 표본 셋, 이미지 둘(`ubuntu-24.04`, `ubuntu-26.04` — 뒤의 것은 spike 018 의 질문이다)이다.

## What to Expect

- 방식마다 처음 실행과 재실행의 벽시계 시간, 프로젝트별 시간.
- 프로젝트 여섯의 진단이 예상과 같은지 (옛 주소 · 묶음 16줄 `exit 2`, 기본만 18줄 `exit 2`, 끄는 설정 15줄 `exit 2`, 기본 + Riverpod 21줄 `exit 2`, 기본 + codegen 13줄 `exit 0`).
- plugin 을 쓰는 넷은 그 실행의 상태 폴더에 plugin 폴더가 하나, 쓰지 않는 둘은 0개.
- 로그의 `SPIKE017_RESULT {…}` 한 줄이 그 job 의 결과다.

### 1. 로컬 연습 (2026-10-12, Dart 3.13.4, macOS, 프로세서 10개)

스크립트가 도는지 보려고 방식마다 한 번 돌렸다. 두 방식 모두 확인 24건이 성립했다 (`results/local-seq.json`, `results/local-par.json`).

| 방식 | 처음 실행 | 재실행 |
|---|---|---|
| 차례로 | 92.7초 | 23.1초 |

- 결과는 `collect.py` 가 job 별 시간(GitHub API)과 로그의 `SPIKE017_RESULT` 줄을 모아 `results/run-38216842742.json` 에 썼다.

### 4. 결과가 같았는가

- job 12개 × 확인 24건 = **288건이 모두 성립했다.** 처음 실행과 재실행, 차례와 한꺼번에, 두 이미지에서 프로젝트 여섯의 줄 수와 종료 코드가 로컬의 예상과 같았다 — 16 / 16 / 18 / 15 / 21 / 13 줄, `exit` 2 / 2 / 2 / 2 / 2 / 0.
- plugin 을 쓰는 넷은 그 실행의 상태 폴더에 plugin 폴더가 하나씩, 쓰지 않는 둘은 0개였다. stderr 에 plugin 준비 실패의 머리말이 나온 실행은 없다.
- **한꺼번에 띄운 처음 실행 여섯 번이 모두 통과했다.** 이 실행에서 plugin 을 쓰는 넷은 `riverpod_lint` · `analyzer` 등 같은 패키지를 같은 pub cache 에 동시에 처음 받는다. 로컬(014)이 지나지 않은 경우다.
- plugin 쪽에서 풀린 버전은 12개 job 모두 `riverpod_lint` 3.1.9 / `analyzer` 14.5.0 / `analysis_server_plugin` 0.3.24 다 (로컬과 같다).

## Results

**Verdict: VALIDATED** — runner 12개 job 의 확인 288건이 모두 성립했고, 차례 실행이 시간 제한의 절반 안에 끝났다.

1. **지금의 방식(차례로, 상태 폴더는 프로젝트마다 따로)을 여섯으로 늘려도 `timeout-minutes: 10` 안에 넉넉히 든다.** 분석 146 ~ 191초, job 전체 약 3분 20초 ~ 4분 20초다 (재실행을 뺀 값). 014 의 추정(약 4분 20 ~ 30초)은 잰 범위의 위쪽 끝이었다.
2. **한꺼번에 띄우면 분석이 69 ~ 95초로 약 절반이 된다.** job 전체로는 약 1분 55초 ~ 2분 40초다 (재실행을 뺀 값 114 ~ 158초). 여섯 번 모두 결과가 같았다. (2026-10-12 wrap-up 에서 `results/run-38216842742.json` 으로 다시 세어 고쳤다 — 앞서 적은 "126 ~ 158초" 는 `ubuntu-24.04` 의 표본 셋만의 범위였고, `ubuntu-26.04` 의 셋은 136 / 133 / 114초다.)
3. 진단은 어느 방식 · 어느 이미지에서도 로컬과 한 줄도 다르지 않았다.

Phase 3 의 계획이 가져갈 것:

1. **`tool/verify.dart` 를 차례로 돌리는 지금의 구조 그대로 여섯으로 늘려도 된다.** 시간 제한 때문에 구조를 바꿀 까닭이 없다. `timeout-minutes` 는 10 으로 둬도 가장 느린 표본(258초)의 두 배가 넘는다.
2. 한꺼번에 띄우는 것은 "자동 점검 한 번에 약 1분 30초를 줄이는" 선택지다. 넣는다면 상태 폴더는 지금처럼 따로 주고, 화면은 여섯이 다 끝난 뒤에 정해진 순서로 찍는다 (014). 넣을지는 계획이 정한다.
3. 03-CONTEXT.md D-03 이 소유자에게 밝힌 "자동 점검이 약 2분에서 약 4분 15초로 늘 것" 은 잰 범위(3분 20초 ~ 4분 20초) 안에 있다. D-09 가 phase 끝에 보기로 한 "여섯으로 늘어난 검증이 시간 제한 안에 끝난다" 는 실제 `tool/verify.dart` 로 한 번 더 본다 — 여기서 돌린 것은 spike 의 스크립트다.

확인하지 않은 것:

- 표본은 칸마다 셋이다. 한꺼번에 띄운 실행이 "드물게" 깨지는지는 처음 여섯 번 · 재실행 여섯 번으로는 알 수 없다 (008 에서 빈 상태 폴더를 **함께** 쓴 실패는 40번 중 1번이었다. 여기서는 상태 폴더를 따로 줬다).
- 실제 `tool/verify.dart` 를 여섯으로 늘린 것. 규칙 검사와 화면 출력의 시간은 여기에 들어 있지 않다 (지금의 `verify` 에서 그 몫은 몇 초다).
- 끄는 설정용 프로젝트는 014 와 같은 가벼운 옵션(plugin 진단 하나를 끔)이다. 실제 프로젝트는 샘플이 더 많다.
- `base_riverpod` 의 재실행이 긴 까닭.
- macOS / Windows runner, SDK 캐시(`cache: true`)를 켠 경우.

원본: `results/run-38216842742.json` (runner, job 15개), `results/local-seq.json` · `results/local-par.json` (로컬 연습), `spike-017-018-runner.yml` (임시 workflow 의 사본), `collect.py` (결과를 모은 도구).
